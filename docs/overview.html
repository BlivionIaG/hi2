Start with three decisions:

  1. Inputs and recipe. Check model eligibility. Keep calibration, tuning and final-test data separate.
  2. Acceptance. Set an allocation budget, then measure the output. Allocation error is not a final quality guarantee.
  3. Execution. Use the CLI for direct work or durable jobs and MCP for reconnectable automation. Native serving needs a separate runtime.

1. Follow the quantization workflow

With calibration, collect activation statistics and build an error table for each eligible weight row. Data-free runs use a different path.

Code: layerwise.py, stats.py, calibrate.py

PTQ covers statistics, allocation and encoding. With calibration, the normal CLI recipe then runs layer-wise QAD and the default preset's final logit-KL training phase. Use --no-qad for PTQ only. Check phase records for skipped work.

Final-KL training is not independent final evaluation. Validate and evaluate the committed output on untouched text.

2. Understand one stored row

Each row contains blocks of 16, 32 or 64 weights. The normal search selects INT2 or INT4 codes. INT8 is also supported when requested; it is not a default candidate.

A block stores two parameter bytes, lo_u8 and step_u8. Three fp16 constants per row decode these bytes into lo and step. Weight reconstruction is w = fp16(lo + code * step). Optional smoothing and order-16 Hadamard rotation also affect the stored basis.

The format reference defines exact rounding, offsets and metadata. This page does not define a second serialization contract.
