# Calibration and held-out/OOD sets v2 for Inkling-2-Mini

Status: staged, built and verified on the CPU of the build box on 2026-11-24
(`stage4/calib_v2`). **Nothing here has run on a GPU.** No quality result is reported or
implied: this document describes data, a gate report and cost estimates, and nothing about a
quantized model's output.

Why v2: the stage-4 set (`docs/inkling-source.md`) is 2048-token windows of mostly English
chat, tool use as plain text, arithmetic and technical text, and the only OOD sets are 17
windows of English Wikipedia and 17 of vLLM docs (stage 4, 2048 tokens each). The deployment
target (HI2 at 3.5 bpw, the routed experts quantized, the rest bf16) is used by a coding agent
on long inputs in several languages, so the set that fits the quantizer and the set that judges
it must contain those shapes.

Scope and method: every staged record is real text from a named public source, a public code
tree on the box, or this repository. Nothing here is generated by a model and no private data
is used. The agentic turns are rendered with the stock Inkling chat template, the same
`chat_template.jinja` the model will see. The only synthetic text is the macOS harness output
in the unit tests. Measurements in this document are CPU runs of the builder and the evaluator
on the box; memory and time figures for a GPU are marked `[INFERENCE]`. No quality result is
reported or implied.

## What is in it

`experiments/inkling_build_calib_v2.py` has four subcommands: `stage` (render and stage the
sources as `<category>.jsonl`), `build` (dedupe, split, window, gate, write the arrays and
`manifest.json`), `ood` (a held-out set from sources that are in no staged category) and
`verify --production` (re-hash every file, re-check the schema and every hard gate).

Every staged record carries `text`, `category`, `language`, `source` and `license`; the
manifest aggregates the same fields per window and adds `license_classes`, so a consumer can
audit the licence of every window's documents. "Local project trees" are public source trees
present on the build box; no private data is used.

The accepted SPDX set is apache-2.0, mit, bsd-2-clause, bsd-3-clause, cc-by-4.0,
cc-by-sa-4.0, isc, unlicense, zlib and public-domain, plus SPDX expressions of those joined
with `OR`, `/` or a parenthesised `AND` accepted only when every part is permissive; an
unknown licence is refused at `stage` and re-checked at `build`. The Linux driver rust text is
GPL-2.0 (`gpl2` class). The default build includes it; `--exclude-license gpl2` builds the
same staging without every `gpl2` document before dedupe/split and is written to
`stage4/calib_v2_nocopyleft`. Both variants are verified; use the no-copyleft one when the
calibration text itself must stay permissive. The SQL corpus is read from the cached
`sql_create_context_v4.json` (`b-mc2/sql-create-context`, cc-by-4.0) and needs no network; the
`deepmind/code_contests` and `open-r1/codeforces` streamers reported `OfflineModeIsEnabled` on
the box and are absent from this build, so the code set beyond SQL is the local trees and the
cargo crates. The stage log records each skip.

The tool schemas and calls are native turns: a ToolACE record's tools become a `tool_declare`
system turn and its call/result pair becomes `role: tool` turns with `tool_calls`/`tool_call_id`
rendered by the Inkling chat template; the Hermes records already carry those turns. The
agentic_bench system prompts are the real coding-agent ones, not a paraphrase.

Hard floors, checked as gates and re-checked by `verify --production`: agentic has at least
60 held-out and 60 calibration windows (it used to share the 16 of the other categories);
Shell, SQL and TypeScript each have at least 16 held-out and 16 calibration windows of 2048
tokens. JavaScript cannot meet 16: the trees supply 13 `.js`/`.mjs`/`.cjs` documents, far too
short to make 16 windows, so its count is recorded and no JavaScript floor or per-language
claim is made. `build` exits 1 when any floor fails; the manifest's `gates` block has the exact
numbers and the failed detail string.

Long-context documents are coherent, not random concatenation: PG19 books and repo files are
sliced as one contiguous document, and the agent transcripts are one multi-turn session per
system prompt. A window never mixes documents. Long windows exist at 8192, 16384 and 32768
tokens (the checkpoint's `mtp.config.max_position_embeddings` is 1,048,576, so the cap is the
data, not the model); the same source documents feed the three lengths, and a document shorter
than a length contributes only to the shorter ones.

## Calibration / held-out split

`--exclude-license` is applied before anything else. Then dedupe: exact sha256 (a document is
never repeated), then near-duplicate shingles per category (a document whose 64-character
shingle set overlaps an already kept document by 0.5 or more is dropped; shingles are sampled
every 8 characters to keep a 100 MB staging tractable). The split is by document, stratified by
category and language (`_split`): a document is never in both splits, and a small language is
guaranteed its share instead of losing every document to the global 20 %. Within a group the
documents are ordered largest first (sha256 as the tiebreak) and each goes to the side with the
lower fill ratio; this is deterministic, and it stops a group of one large and many tiny files
from putting every large file on one side and leaving the other without enough tokens for a
window (the first SQL split did exactly that). Measured: **18 exact duplicates dropped, 1243
near-duplicates dropped**. Almost all near-drops are ToolACE records that repeat a rendered
tool-schema prefix; the surviving agentic records are the distinct sets. The 24
`agentic_bench` transcripts carry a `dedupe_text` of the prompt and task names plus the task
body, so their three shared system prompts do not collapse them to one document; their full
text, with the real repository tool results, is what the split and windowizer see. They are
also placed first in the split's window order, so the capped agentic windows include them
before ToolACE's larger volume fills the cap. After windowing, every
held-out window is checked against the calibration tokens of its category (32-token shingles,
sampled every 8 tokens). A window at or above 0.5 is a leak that the sampled text dedupe
missed; it is dropped and the count recorded. Measured: **one held agentic window was
dropped** (leak 0.929: an `agentic_bench` transcript whose system prompt also appears in
calibration); the kept maxima are 0.4794 (`code/json`) and 0.346 (agentic). The manifest keeps
`mean`/`p99`/`max` of the kept windows, `leaked_max` before the filter and `dropped`.

Calibration: **781 windows / 3,237,888 tokens**. Held-out: **820 windows / 2,580,480
tokens**.

## Minimum detectable difference

The stage-4 mixed-set KL was 0.1197 ± 0.0113 (sem over 96 windows), so the per-window standard
deviation is σ ≈ 0.0113·√96 ≈ 0.111. The values below use that σ for every category
[INFERENCE: long windows may have a smaller σ because the KL is averaged over more positions,
so the long-context MDE may be optimistic; a category with a different distribution can have a
larger σ]. MDE is the 80 %-power, two-sided 5 % detectable difference against a fixed value
(`1.96·σ/√n`) and between two independent equal-n sets (`3.96·σ/√n`, from
(1.96+0.84)·√2); a paired per-window comparison uses the variance of the per-window difference
(usually far below 2σ²) and is the right test once both models are scored on the same windows.

| Set | n | MDE vs fixed | MDE, two sets |
| --- | ---: | ---: | ---: |
| agentic | 63 | 0.0274 | 0.0554 |
| code | 285 | 0.0129 | 0.0260 |
| general_chat | 32 | 0.0385 | 0.0777 |
| long_context | 56 | 0.0291 | 0.0587 |
| long_context, 32k | 16 | 0.0544 | 0.1099 |
| math_reasoning | 30 | 0.0397 | 0.0803 |
| multilingual | 354 | 0.0116 | 0.0234 |
| multilingual, de (smallest) | 21 | 0.0475 | 0.0959 |
| code, c (largest) | 32 | 0.0385 | 0.0777 |
| code, typescript | 29 | 0.0404 | 0.0816 |

A category-level KL difference of ~0.013 is detectable for code, ~0.012 for multilingual,
~0.027 for agentic and ~0.03-0.04 for general/math/long context; per-language claims are at
best ~0.038-0.048. The 32k long-context set alone supports ~0.054. JavaScript's 32 windows are
one document and typescript's 29 are a small sample; both are exploratory.

## Scoring

`experiments/inkling_kl_eval.py` is extended without changing the old results:

* A single-file `--ids heldout_mixed_ids.npy` still splits the file into windows and scores
  the default groups, routing, tokens and out; the result and the out JSON are unchanged.
* `--ids DIR` (a v2 directory) scores every file of `--split` (default `heldout`; `calib` and
  `ood` too) with its own window length in one model load. The key is the file name
  `split_category__language__length_ids.npy`; every file is checked against the manifest's
  sha256 and size before it is loaded.
* `--position-buckets 0-2048,2048-8192,8192-16384,16384-` adds the KL of each position
  bucket. The ranges are half-open and per window (`0-2048` is tokens 0..2047 of the window,
  not global positions), the last bucket takes every position past its lower bound.
* `--batch-windows N` runs the layer program on at most N windows per forward (0, the
  default, is every window at once, the stage-4 behaviour); the 8k/16k/32k windows need a
  small N to fit the cards.
* `--groups`, `--teacher-cache`, `--routing-log` and `--int8-class` refuse a directory with a
  message: they are per-window or per-file and the set path scores the whole student in one
  load.

`result["eval_set"]` is `{dir, split, sets, category, language}`. `sets[key]` has the file's
category, language, length, windows, the summary and `position_buckets`; `category` and
`language` pool the same windows. The old keys (`student`, `gates`, `seconds`, ...) are
unchanged. Loading a directory refuses a manifest with `ok=false`, a missing gate block or a
file whose sha256/size differs. The tests cover the loader (schema, gates, sha256), the
position buckets and their pooling, and one end-to-end set run with a tiny model and two
windows of different lengths (4 and 8 tokens); the single-file path keeps the old tests.

The production command:
`--src STOCK --dst HI2 --ids <calib_v2> --split heldout --position-buckets
0-2048,2048-8192,8192-16384,16384- --out ...`.

## Costs on the two V620 cards

Measured on the CPU of the build box: 3.66 ms/token for the layer program and 1.9 s / 6.8 s
per forward for 8k / 32k windows (stage-3/4 numbers, 2 x 24 GiB V620, no quantized expert path).
For one 8k window, teacher and student passes: 1.9 s each, ~4 s; 32k: ~14 s. **Estimated**
[INFERENCE] for the v2 held-out set: 56 long windows (20 x 8k, 20 x 16k, 16 x 32k) at 2
forward passes ≈ 20·2·1.9 + 20·2·3.8 + 16·2·6.8 ≈ 446 s ≈ 7.4 min, plus the 764 short
windows ≈ 764·2·0.47 ≈ 718 s ≈ 12 min; the 820 held-out windows are ~19.5 min. The 96
calibration long windows (32 at each length) are ≈ 32·2·(1.9+3.8+6.8) ≈ 800 s and the 685
short calibration windows ≈ 644 s, so the full v2 with a teacher cache is ≈ 45 min on the
cards. These are scale-ups of the stage-3/4 per-forward numbers, not a measurement of the v2
sets.

Memory for one 32k window: hidden 2304, 24 layers, 8 KV heads of 128; `local_layer_ids` has 20
layers with a 1024 window and 4 global layers (5, 11, 17, 23): the KV cache is
(4·32768 + 20·1024)·8·128·2 B ≈ 0.31 GB and the activation row is 2304·2 B ≈ 4.5 KiB per
token. The attention scores of the four global layers are 4·24·32768·32768·2 B ≈ 206 GB if the
fused flash kernel is not used, so FA is mandatory. The float32 logits are the other wall:
32768 positions × 201,024 vocabulary × 4 B ≈ 24.5 GiB **per model**, so a full-logit 32k pass
does not fit one 24 GiB card; the evaluator must chunk positions (a 4k chunk is ≈ 3.1 GiB) or
score in bf16 (≈ 12.3 GiB). The layer-program stats pass holds one float32 hidden row of
32768 × 2304 × 4 B ≈ 0.28 GiB per window, so `--batch-windows 1` is the only safe setting at
32k. The teacher cache scales from 8.1 GiB for 96 × 2048 windows (≈ 86 MiB/window) to
≈ 1.4 GiB for a 32k window [INFERENCE: linear in tokens]. The stage-3/4 measurement (peak
state 104,472 MiB) does not cover any of these 32k paths.

## GPU smoke checklist (first lease, 2 x 24 GiB; no GPU has run this yet)

1. `experiments/inkling_build_calib_v2.py verify --out <calib_v2> --tokenizer <stock>
   --production` on the box's copy and the same for `stage4/calib_v2_nocopyleft`: both must
   exit 0 with `"problems": []`; do this before anything GPU.
2. **Max feasible sequence for the layer-program stats pass.** Load the stock checkpoint with
   FA enabled and run one window at 2048, 4096, 8192, 16384, 32768 and 65536 tokens with
   `--batch-windows 1`; record peak memory and the largest length that completes without OOM
   or NaNs. The expected ceiling is between 16k and 32k on 2 x 24 GiB if attention is fused
   and the cache is not materialized [INFERENCE]; step down by 1024 from the first failure to
   find the exact limit.
3. **Max feasible sequence for the float32 evaluator.** The same ladder through the KL
   evaluator on one window (teacher and student), recording peak and the largest length;
   confirm that its position chunking keeps the 32k logits under the card limit and that the
   float32 teacher/student logits agree with the bf16 path to the usual tolerance on a 2k
   window. Expected ceiling: 16k-32k with chunking, less without [INFERENCE].
4. **Set fidelity.** `--ids <calib_v2> --split heldout --position-buckets
   0-2048,2048-8192,8192-16384,16384- --batch-windows 1` must score one window of each of
   the 20/20/16 lengths and populate all four buckets (a 2k window populates only `0-2048`);
   score the same windows one `.npy` file at a time through the single-file `--ids` path and
   compare the per-window KL. Check the no-copyleft manifest scores the same short windows
   with no `gpl2` document in any row.
5. Record the actual bytes/seconds per window in the run's `seconds` block and update this
   section with the measured values.

## Limits and risks

* No GPU result: the 3.5 bpw target, the clipping/search and the KL values are untested by a
  quantized model; do not quote a quality number from this set until a lease has run it.
* The agentic set is rendered from real tool schemas and prompts, but the model's own
  generations are not in it; it measures the read of tool turns, not multi-step success. The
  held-out agentic side has 63 windows (the 64-window cap less the one leak drop), so it
  cannot grow without raising `MAX_WINDOWS`; the floor is 60. The local `agentic_bench`
  transcripts contribute 8 calibration and 1 held-out window; the rest is ToolACE.
* Near-duplicate dedupe dropped 1243 of 3024 staged agentic records because they repeat the
  rendered tool-schema prefix; the surviving 63 held-out windows are from distinct records,
  but the de-duplication rate should be read before adding another ToolACE-sized source.
* The Linux rust text is GPL-2.0 (see above): the default manifest includes it and
  `stage4/calib_v2_nocopyleft` is the same build without every `gpl2` record.
* Long windows are 8192-32768 tokens; the checkpoint accepts 1M, so >32k quality is not
  measured. The 32k held-out side has 16 windows, so its own MDE is ~0.054.
* JavaScript's held-out windows are contiguous slices of one minified bundle; typescript has
  29 windows. Both are exploratory; shell and SQL now clear 16 held-out windows, so a
  per-language claim for them is supported at the MDE above.
* The positional buckets are per-window half-open ranges; a 2048-token set has only the first
  bucket, so a per-position claim for the old sets is not possible.
